# Security: the embedded Pluto scripting runtime

`rana-socket` embeds **Pluto** (a Lua 5.4/5.5 fork) and runs `.pluto` scripts
that are **generated by an LLM at runtime** (e.g. `ask.pluto`, `lookup_machine.pluto`).
These scripts are **untrusted**: a model can hallucinate calls it was never
supposed to make. The runtime is therefore locked down by default and requires
no configuration to stay safe.

## Threat model

| Capability | Risk if exposed to a malicious/hallucinated script |
| --- | --- |
| `os`, `io` | Arbitrary process execution, filesystem read/write, env leaks |
| `ffi` (`lffi.cpp`) | `ffi.open` → load arbitrary `.so`; `ffi.alloc/write/read/callback` → native memory R/W and code execution |
| `socket` / `http` / `tls` | Direct outbound network: exfiltration, SSRF against internal services |
| `crypto` / `wasm` | Decryption of secrets, arbitrary code via WASM |
| `load` / `loadfile` / `dofile` | Execute arbitrary/compiled Lua from disk or a string |
| `package.*` (`require`, `loadlib`) | Load any installed C/Lua module, including the above |
| Compiled Pluto bytecode | Bypass source review / hide logic in a binary blob |

## Defense layers (all on by default)

### 1. Compile-time flags (predep `make` stage `pluto`, `predep.toml`)
Pluto is **not** compiled in-tree. `predep` clones it and builds
`vendor/pluto/src/libpluto.so` via Pluto's own Makefile (`builder = "pluto"` →
`[[stages]] name = "pluto" type = "make"`), passing the hardening flags through
`MYCFLAGS`:
- `PLUTO_DISABLE_COMPILED` — reject precompiled bytecode; only source may load.
- `PLUTO_NO_BINARIES` — disables `ffi.open` / `os.execute` / loading of `.so`.
- `PLUTO_DISABLE_HTTP_COMPLETELY` — makes Pluto's `http.*` fail closed even
  if the library were somehow loaded.
- `PLUTO_ETL_ENABLE` / `PLUTO_ILP_ENABLE` — enable Pluto language features the
  scripts rely on.
`rana-socketd` links the prebuilt `libpluto.so` (see `socket/premake5.lua`) with
an rpath of `$ORIGIN` + the build path, and `predep install` ships the `.so`
next to the binary.

### 2. Runtime lockdown (`LuaRuntime::new_state`, `luafunctions.cpp`)
**Always applied — there is no config toggle.** Instead of Pluto's
`luaL_openlibs(L)` (which opens *everything* and, worse, preloads `ffi`,
`socket`, `http`, `crypto`, `wasm` into `package.preload` so `require` bypasses
global stripping), we call:

```cpp
luaL_openselectedlibs(L, kRanaLoadLibs, 0);
```

- `kRanaLoadLibs` only opens: `_G`, `package`, `coroutine`, `debug`
  (needed for Pluto's own startup `debug.getinfo`, then stripped), `math`,
  `string`, `table`, `utf8`, `json`, `base64`, `regex`.
- The **preload mask is `0`** → nothing is registered for `require`.

After opening, the sandbox additionally:
- Strips globals: `io`, `os`, `debug`, `load`, `loadfile`, `dofile`, `ffi`,
  `socket`, `http`, `tls`, `crypto`, `wasm`.
- Empties `package.path`/`package.cpath`, nils `package.loadlib`, empties
  `package.preload`/`package.loaders`, and installs a **single restricted
  searcher** that resolves only `require("lib.<name>")` →
  `scripts_dir/lib/<name>.lua` (reviewed helpers; module names are `[A-Za-z0-9_]`
  segments, so no separators/traversal). Everything else — `ffi`, `socket`,
  `http`, `os`, ... — resolves to nothing.
- Purges `package.loaded` for all the above so a library cannot be resurrected.

### 3. Bridge allowlists (the only sanctioned escape hatches)
All privileged actions go through the `rana.*` C bridge and are gated:
- `rana.spawn(...)` — only binaries present in the `init.pluto` allowlist.
- `rana.dispatch(...)` / `rana.respond(...)` — only `[commands.allowed]` keys.
- `rana.http_post(...)` — only hosts present in the endpoint allowlist.
- `rana.audio.decode_to_wav(...)` — in-process codec; no shell, no network.
- `rana.script_metas()` — read-only startup metadata per script (`description`,
  `keywords`, `danger`, and the `external_egress` opt-in). Drives the fuzzy
  pre-router and the inbound routing gate below; carries no secrets.
- `rana.provider_post(kind, index, ...)` — the **only** TLS path; `kind`
  (`"llm"`/`"stt"`) and `index` select a config-owned `[[llm.provider]]` /
  `[[stt.provider]]` entry (scripts never name the host). See "Outbound egress
  tiers" below.
- `rana.http_post` uses our own `http_do` (getaddrinfo + HTTP/1.1 with send/recv
  deadlines) and only talks to allowlisted hosts; it is **not** Pluto's `http`
  library. It returns `(ok, body, status)`; `status == 0` marks a transport
  failure (the only case on which a provider chain advances). In the default
  (no-TLS) build `https` URLs are rejected at the scheme check rather than
  silently connecting in the clear; TLS exists only behind the opt-in build flag
  and only for `rana.provider_post` (below).

### 4. Outbound egress tiers
Each hop is an ordered **provider chain** (`[[llm.provider]]` / `[[stt.provider]]`).
Providers are tried in order; a provider answers when it returns 2xx (or a live
4xx/5xx — the upstream's own answer), and only a **transport failure/timeout**
(status 0) advances to the next entry. The URL scheme decides the tier, and the
optional `type` field must agree with it:

- **Local tier** — `type = "local"` (`http://`). The host must already be listed
  in `rana.allow_endpoints(...)` in `scripts/init.pluto`; reached via
  `rana.http_post`/`rana.provider_post`. This is the LocalAI/Whisper path.
- **Hugging Face tier** — `type = "huggingface"` (`https://`), reached **only**
  via `rana.provider_post`. Scripts cannot add to it or name its host; generic
  `rana.http_post` can never reach it.

Outbound to the Hugging Face tier is deny-by-default at every layer:
1. **Build** — off unless the daemon is built with the `--tls` premake flag
   (`RANA_ENABLE_TLS`). A no-TLS build has **no** OpenSSL linkage, compiles no
   TLS code, and rejects every `https` URL. Ablation, not policy. Static OpenSSL
   is preferred automatically where the distro ships `libssl.a`/`libcrypto.a`;
   force the dynamic `-lssl -lcrypto` path with `--tls-dynamic`.
2. **Config** — a `huggingface` provider needs an `https` url and its `api_key`
   (an `api_key` on a `local` provider is rejected outright, so the token cannot
   leak over cleartext; a `type`/scheme mismatch is rejected at load).
3. **Policy** — `[security].external_egress = false` hard-disables the tier even
   when configured (fleet/incident kill switch).
4. **Per call** — the calling hop may pass `{ cloud = false }` to skip every
   huggingface provider for one request (e.g. not shipping a particular
   transcript/recording to a third party).

The bearer token (`api_key`) is **injected by the C bridge** as
`Authorization: Bearer …`; it is never returned by any `rana.*` getter, never
logged, and any script-supplied `Authorization` on a huggingface call is
discarded. TLS verification is mandatory: peer certificate **and** hostname are
checked against the request host, with TLS 1.2 minimum.

### 4a. Inbound routing gate (answers from a huggingface provider)
Egress is only half the risk: a remote model's *answer* is untrusted (it can be
steered by whatever the microphone picked up), so acting on it is gated too.
- An answer that came from a `type = "huggingface"` provider is stamped
  `external` by `lib/llm.pluto` from the provider that **answered** — never from
  the reply text — so the model cannot spoof it.
- `scripts/lib/route.pluto` then refuses to dispatch or relay an external answer
  to any script that has not opted in with `rana.flags.EXTERNAL_EGRESS` in its
  `meta.flags` (read back via `rana.script_metas().external_egress`). **Off by
  default**: a remote model can reach nothing until the operator opts scripts in
  — including `speak` (itself a script), if replies should be spoken.
- A refusal never executes and never reaches the peer. `scripts/lib/refuse.pluto`
  owns the ladder: speak a short reason (only if `speak` opted in), else log and
  drop, else `SAFETY_GATE_FAILED`. It is isolated and read-only.
- Local (non-external) answers are unaffected — the local model stays trusted.

### 5. Script registration
- The daemon scans `scripts/*.pluto` at startup and reads each script's `meta`
  (name, description, actions, params, timeout, examples, flags). Scripts are
  self-describing and must declare what they do; `init.pluto` only registers the
  binary/endpoint allowlists.
- A per-script execution timeout bounds blast radius. Scripts cannot touch the
  filesystem directly (`io`/`os` are stripped); the only file access is the
  host-side `lib/` searcher, which reads the reviewed `scripts/lib/*.pluto` only.

## In-process hops
`talk.pluto` reaches `stt.pluto` and `ask.pluto` through the generic
`rana.dispatch` hop; `ask.pluto` builds its intent from `lib/llm.pluto` +
`lib/fuzzy.pluto`. Hops run in the **same locked-down state** — the runtime does
not grant them extra privileges. The one confirmation gate is `power.pluto`:
a destructive power action requires the client's explicit `params.confirm` and
otherwise fails closed (`SAFETY_GATE_FAILED`).

## Operational rules
- **Never** switch `new_state()` back to `luaL_openlibs`. That silently re-opens
  every dangerous library.
- Keep the compile-time flags above. They are belt-and-suspenders on top of the
  runtime mask.
- Treat every file under `scripts/` as untrusted input. Review generated
  scripts before persisting them.
- Optional deeper hardening (deferred): define `PLUTO_FFI_CALL_HOOK` /
  `PLUTO_HTTP_REQUEST_HOOK` to reject any FFI call / HTTP request at the
  call-site. The runtime mask already makes these unreachable, so this is
  defense-in-depth only.
